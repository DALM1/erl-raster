# erl-raster

**移动端的自适应光栅化：测量哪个引擎更快，然后让设备自己决定。**

`erl-raster` 是一个小型 Rust 工作区，它诚实地回答一个问题，就在它正在运行的那台机器上：*对于这一段绘制，现在 CPU 还是 GPU 更快，以及什么时候值得切换？* 它不替代图形引擎，也不介入某个图形引擎。它光栅化叶子节点，测量这件事的开销，然后进行仲裁。

## 1. 我们遇到的问题

我们用 React Native 构建一个移动应用。滚动一个会话列表并不流畅，而打开一个会话时，在第一帧稳定下来之前也多停顿了一瞬。性能剖析里没有任何东西说是"JavaScript 线程"，没有说是"布局"，也没有说是"网络"。丢帧发生的地方，正是原生应用丢帧的地方，也就是光栅化，而这是我们这套技术栈从未有理由去关注的那个流水线环节。

追查它，得到了一个其实跟我们应用本身无关的发现。

**两个平台都允许一个应用用 CPU 或 GPU 来光栅化一段内容，而两个平台都没有测量哪一个更快。**

- 在 iOS 上，`CALayer.draw(in:)` 给出一个 CPU 上下文，`CAMetalLayer` 给出一个 Metal drawable，而 `shouldRasterize` 会把一棵子树的成本转移进一次性的离屏光栅化中。这些都是真实的流水线选择，而它们一次一层地、由人手存在。
- 在 Android 上，`View.setLayerType(LAYER_TYPE_SOFTWARE)` 把一棵子树强制到 CPU 上，`SurfaceView` 或 `TextureView` 交给你一个你自己拥有的 surface，而 `RenderEffect` 在硬件流水线内部用 GPU 运行模糊和颜色处理。同样，是真实的选择，由人手作出，一次一个视图。

所以这根杠杆是存在的。不存在的，是任何去拉动它的东西。一个开发者想知道某次模糊应该在这台手机的 CPU 还是它的 GPU 上运行，就得写一个基准测试，运行它，祈祷手机没有发热，然后针对一台他再也不会见到的设备把答案写死。

而把那个基准测试写正确，出奇地难。我们自己的第一次尝试就以各种方式出错了，产出了自信却毫无用处的数字：

- 在一个它已经触碰过的缓冲区上测量的 kernel，比在它刚刚收到的缓冲区上测量的同一个 kernel 最多快五倍，所以那个天真的循环测量的是缓存，却把它称作计算。
- 先跑完整条流水线，再跑完另一条，会给后者一个时钟已经升频的好处，而给前者承担把它升上去的成本。
- 一台已经降频的手机，基准测试的是它降频后的自我，而在那个状态下采集的性能档案所描述的，是一台已经不存在的设备。
- 切换流水线不是免费的。绑定、描述符、栅栏，有时还有一次传输。一个在百分之五的收益上就切换的调度器，很容易把更多时间花在切换上，而不是绘制上。

最初引发这一切的那个性能缺陷，如今已在应用本身中被理解并修复。它所暴露出来的，是这个仓库所填补的缺口：CPU 与 GPU 之间的仲裁，是每一个渲染技术栈都会作出的一个决定，作得很糟，而且靠人手。

## 2. ERL Raster 是什么以及它拒绝成为什么

`erl-raster` 是一个**带仲裁层的光栅化引擎**。你为一个帧描述一批绘制，连同目标一起交给它；库会在它自己的流水线中选出一条被预测为最快的来运行它，而且是在设备实际所处的条件下。

它不是一个框架，不是一个合成器，也不是 Core Animation、HWUI 或 Skia 的替代品。它无法截获另一个框架的绘制调用，它也不去尝试。兼容性问题是由设计来解决的，而不是靠指望：

- **一个 API，永远不是一个 hook。** 没有 swizzling，没有类替换，没有未定义行为。这正是它可分发的原因，无论是在应用商店还是在包注册表上。
- **一个永久的、永不移除的 CPU 回退。** 标量 CPU 路径永远在候选集合里。采用这个库的最坏情况，就是它跑得和参考实现一样快。
- **一条确定性的参考路径。** CPU 参考实现从头到尾只用整数，所以一致性比较是逐比特的，而不是近似的。一个产生偏差的后端就是错的，而不是"足够接近"，它会被关闭，而不是被悄悄容忍。

一句话版本：*把绘制写一次，然后让仲裁来挑选引擎。*

## 3. 设计所围绕的四个陷阱

### 3.1 被缓存扭曲的基准测试

修复之道不是更好的循环，而是两次测量，以及一条关于哪一次适用的规则。

- **两种状态，都被存储。** `Regime::Hot` 复用目标，并让源保持驻留，这描述的是一种在已经处于流转中的数据上重复进行的操作，比如每一帧都重绘的字形图集。`Regime::Cold` 分配一个全新的目标，并在迭代前把缓存清刷一遍，这描述的是一个屏幕的第一帧，或者一张正在被解码并缩放的图像。在冷状态下，迭代之间会写入一个十六兆字节的缓冲区，这超过了每一台手机和大多数笔记本电脑的最后一级缓存，而且这次分配有意地落在被测区域之内。
- **由宿主来挑选状态，而不是由基准测试。** 只有调用方知道某一帧是在重复驻留的工作，还是在接收新的源。这正是 `FrameContext::regime` 所携带的信息。
- **预热会被丢弃。** 一条流水线最初的若干次迭代，包含它的第一次分配、第一次着色器编译，以及其后所有内容的缓存填充。默认的 harness 配置会在保留 60 次之前丢弃 10 次迭代。

### 3.2 切换流水线的代价

- **决策的单位是批次，而不是图元。** 一次切换要为绑定、描述符更新和同步付出代价；对每个字形逐一决策，开销会比字形本身还大。一个批次是一个帧的绘制，所以单次切换会在它里面的所有内容上被摊薄。
- **切换成本是被测量出来的，不是估算出来的。** `measure_switch_costs` 在另一条流水线上的一次加载之后立即运行同一份负载，再减去在同一条流水线上的一次加载之后运行它所花的时间，逐对有序对进行，因为这个成本不是对称的。`SwitchCostModel::between` 对从未被测量过的一对返回 `None`，而 `None` 不会被变成一个默认值：一次未被测量的移动会被拒绝，而不是被假定为免费。
- **每个帧至多一次性能移动。** 第二次性能移动会在它本应改善的那个帧内部把固定成本付两遍。因为现任者*无法*运行该批次而作出的一次移动，不受这个预算的限制，因为它不是无谓的折腾。
- **绝不在关键窗口期内。** 当一个动画被提交、当一个目标被共享，或者当一次捕获正在进行时，宿主会声明某一帧为关键帧。`FrameContext::frozen` 携带这一信息，而支持一次变更的证据会停止累积，而不是被丢弃。

### 3.3 在性能档案之下发生变化的负载

- **不去尝试读取"GPU 利用率"。** 它在这两个平台上都没有暴露给应用。一个繁忙的 GPU 反而会表现为一次不稳定的、从提交到完成的延迟，而这个项目所观察的正是那种方差，而不是一个假设中的仪表。
- **热状态是性能档案身份的一部分，而不是它旁边的一个字段。** `SystemState` 依据设备、平台和热状态为一个性能档案建立键。`ThermalState::permits_absolute_measurement` 仅在 `Nominal` 时为真，而一旦状态不再匹配，运行时就会回退，并不再信任该性能档案。
- **带明确写下的数字的迟滞。** 一个挑战者必须超过现任者的成本，超出的部分要达到被测量的切换成本再加上一个边际，默认是现任者的百分之十，并且必须在连续 3 次评估中都做到，才能取代其位置。一次回归是指一次执行落在它自己预测值的 1.5 倍以上，连续 4 次。

### 3.4 兼容性

- **三个集成层级，从最不侵入到最侵入。** 一个图像生产者（`render(op) -> surface`）完全不需要原生集成，并且能在桌面上的测试 harness 中工作。一个宿主视图，在 React Native 上是一个 Fabric 组件，在 iOS 上是一个叠在 `CAMetalLayer` 之上的 `UIView`，在 Android 上是一个叠在 `SurfaceView` 之上的 `View`，它预留给每一帧都在变化的内容。平台适配器是小的 Swift、Objective-C++ 和 Kotlin 层，用于只有平台语言才能触及的东西：热接口、一个渲染效果、一个视图的 layer 类型。
- **一致性是被验证的，不是被假定的。** 每个后端都会与整数参考实现进行比较，在后端声明自己并非逐比特精确的地方，使用一个显式的、逐操作的容差。一个产生偏差的后端会被禁用，而不是被悄悄近似。
- **不在平台背后做任何探测。** 注册表里包含的是被显式链接进构建里的东西，再加上参考实现。一个没有被链接的 GPU 会连同它缺失的原因一起出现在报告里，而不是以一片空白出现。

## 4. 逐个 crate 的实现

这个工作区是四个 crate。MVP 在 **GPU 桥之外没有任何第三方依赖**：核心、基准测试和调度器都是纯 `std`，这使开源构建在任何机器上都可复现，也让帧路径中没有可能让它停顿的代码。

```
crates/
  erl-raster-core         基础图元和确定性参考实现
  erl-render-backends     各个实现，位于同一份契约之后
  erl-benchmark           测量引擎和设备性能档案
  erl-adaptive-runtime    调度器
```

### 4.1 `erl-raster-core`

平台无关的光栅化，以及每一个后端都必须满足的参考实现。

- `op` 定义了什么可以被请求。`OpKind` 是 `FillGlyphs`、`Resample` 或 `Blur`，刻意就是这三种，因为这三者的行为差异足够大，对它们三者只给一个答案，会对其中两个都是错的：一次字形运行小而分散、受延迟约束；一次重采样是一次流式读取；一次模糊是一次带暂存缓冲区的两趟扫描。每一种都暴露一个以*工作单位而不是时间*表示的 `Work` 成本，因为一个后端知道自己被要求做什么，而只有 harness 能说出它花了多长时间。`Batch` 是决策的单位，而 `OpKindSet` 是一个三位集合，这样每帧的调度器可以在一个寄存器里构建它，永远不必分配。
- `reference` 是确定性路径。从头到尾的整数运算：一个浮点 kernel 在一台 x86 构建机、一台 Apple silicon 手机和一台 ARM Android 设备之间可能有差异，这会让一致性测试要么无法编写，要么永远标红。整数在这三者之间给出逐比特相等的结果。
- `fixed` 存放定点辅助函数，写法上让一个八通道的 NEON 寄存器精确地复现标量值。`image` 存放 `Surface`，一个紧凑排列的四字节 texel 缓冲区，带一个廉价的指纹，用来指出两条后端在*哪里*发生了偏差。`glyph` 存放 `GlyphMask`、`GlyphSpan` 和 `GlyphRun`，其掩码复用方式如同一个文本缓存使用一张图集。`geom` 和 `error` 是支撑类型。`system` 定义 `SystemState` 和 `ThermalState`。
- `workload` 构建公布的负载，在第 5 节描述。

这个 crate 带有 `#![forbid(unsafe_code)]`。那些需要 `unsafe` 的向量化 kernel 位于后端之中，处在使它们可以安全调用的架构检查之后。

### 4.2 `erl-render-backends`

一份契约，若干实现。

- `Backend` 是这个 trait：`capabilities`、`cost_model`、`prepare`、`execute`、`release`。`prepare` 是一条流水线做它只应做一次的工作的地方，这样第一次*被计时的*执行才具有代表性。`execute` 针对一个宿主内存目标运行整个批次，并返回一个 `Executed`。
- `Capabilities` 描述一个后端*是什么*：它服务哪些类别、它接受的最大 surface、它是否逐字节复现参考实现，以及重新进入它是否代价高昂。一个只服务批次一部分的后端根本就不是候选，因为把批次拆到两条流水线上会付出一次切换和一步合成的代价，而 MVP 不做这件事。
- `CostModel` 描述一个后端*花费多少*，用调度器需要独立掌握的四个项来表示，因为它们随不同的东西缩放：每次执行一个固定成本、每个操作一个成本、每个工作像素一个成本，以及每个被移动字节一个成本，后两项以纳秒的千分之一为单位，这样一条快速的流水线才能被表达出来。`from_measurement` 依据一次被测量的时长重建一个模型，而专门的固定成本探针会精化它。
- `CpuBackend::scalar()` 是参考实现，也是回退。`CpuBackend::neon()` 只存在于 AArch64 上，在其他地方返回 `None`，而不是在一个 NEON 名字下交回标量后端，因为一个谎报自己是哪条流水线的后端会毒害性能档案。两种版本是同一个类型，由一个标志区分，而向量化的那个恰好替换了一样东西：字形合成那一行，正是测量把成本归到的地方。重采样是一种 gather，从宽寄存器中获益甚少，而 box blur 的归一化是一次整数除法，在这个架构上没有通道并行的形式，所以两者都留在参考路径上，并且 `Capabilities` 也是这样说的。
- `GpuBackend` 是那道接缝加上设备。`GpuSurfaceBridge` 是三个调用，`device`、`prepare`、`execute`，没有生命周期上的花招：每个平台一个实现，用那个平台的语言，位于一层薄薄的 FFI 层背后。决定性的规则是，目标是**宿主内存**：桥把它上传、绘制，再把结果下载回来，所以那个决定大多数真实情形的传输是在 harness 计时的区域*之内*。一个在一个它已经拥有的纹理上被测量的 GPU 后端，会报出一个好得多的数字，并描述出一个调用方永远不会身处其中的情境。`GpuBackend::absent` 的存在，是为了让报告能说出一个 GPU *为什么*不是候选，而不是悄悄把它省略掉。
- `wgpu_bridge` 是第一个真正的桥，只在 macOS 上编译。四个决策塑造了它：kernel 是 compute dispatch 而不是 render pass，因为一次字形运行必须读取它即将混合的那个像素，而一个 render pass 无法读取它自己的 attachment；一切都是一个就地读写的 storage buffer，而不是纹理，这省掉了一次暂存拷贝和一趟去步长处理；上报的 `Work` 是在宿主上、用参考实现所用的那套裁剪运算计算出来的，因为在设备上统计像素会为了得知宿主已经知道的东西而在每一帧增加一次回读；而测量规则是那道接缝的规则，上传和下载都在区域之内。
- `registry` 是兼容性陷阱落地的地方。不做发现，不做探测。`default_registry()` 首先返回标量参考实现，并在架构有向量化版本时返回向量化版本；`registry_with_gpu` 追加一个被链接进来的桥。

### 4.3 `erl-benchmark`

测量引擎，也是唯一比进程活得更久的东西。

- `stats` 拒绝单独报告一个平均值。既定次数迭代上的中位数和第九十五百分位，因为平均值恰好会掩盖那些可见的东西：那些长帧。`is_conclusive` 防止报告一个由过少样本构建出来的分布。
- `regime` 是 3.1 节的热冷划分。
- `harness` 拥有时钟。`HarnessConfig` 默认是丢弃 10 次迭代然后保留 60 次，两种状态，以及一次十六兆字节的清刷。`run_trials` 让每条流水线对每份负载运行，逐个批次地交错这些流水线，这样两者都不会得到时钟的爬升。`measure_switch_costs` 产生有序对的切换成本。一个 `Trial` 报告 `Measured`、`Unavailable`、`Unsupported` 或 `Failed`，并附带一个原因，所以一条没有运行的流水线是一个发现，而不是一个缺口。
- `profile` 是后续会话据以调度的东西。`DeviceProfile` 持有采集它时所处的 `SystemState`、各个条目，以及切换成本，并写入一种带版本号的文本格式，人可以读、diff 可以审阅。`fastest_for_kind` 从单一类别的负载中回答"在这台设备上，热状态下，谁赢了模糊"，这正是一个关于某个类别的决策如何能从一个包含了它的另一份负载的测量中作出。

### 4.4 `erl-adaptive-runtime`

项目停止测量、开始决策的地方。它不包含渲染代码：各条流水线通过 `Backend` trait 到达。

- `FrameContext` 是只有宿主知道的东西，与库推算出的东西之间的划分。宿主声明状态，以及该帧是否关键。其他一切，也就是仲裁本身，都是库的职责，因为这不是应当要求一个应用去弄对的事情。`AdaptiveRuntime::render` 接收一个批次并返回它渲染出的字节，而调用方从不指名某条流水线。
- `DispatchPolicy` 是数字形式的迟滞：`minimum_gain_percent`（10）、`required_consecutive_wins`（3）、`regression_percent`（150）、`regression_window`（4），以及 `switching_enabled`，后者固定现任者，是项目用来衡量仲裁值多少的 A/B 开关。`gain_clears_the_bar` 刻意就是一个不等式：收益必须偿付这次移动*并且*越过那个边际，所以写不出一个策略，使得一次移动既被批准又不值得。
- `Decision` 携带作出该决策的原因，包括那些不移动的决策，并附上其背后的四个数字：预测的现任者成本、预测的挑战者成本、被测量的移动成本，以及连续胜利次数。这正是让策略可以在没有手机的情况下被测试的原因，也是让一个行为出错的调度器可以被调试的原因。共有十一个原因，其中包括 `GainBelowSwitchCost`、`SwitchCostUnknown`、`ChallengerNotProven`、`CriticalWindow`、`SwitchBudgetSpent`、`StaleProfile`、`IncumbentCannotServe` 和 `UnavailableFallback`。
- `AdaptiveRuntime` 持有五条规则。现任者绝不因为慢而被撤下，只会被更好的东西取代；不存在"没有流水线"的状态。挑战者必须反复取胜。一次移动必须用被测量的纳秒来偿付它自己，而一次未被测量的移动会被拒绝。每个帧至多一次性能移动。性能档案只在采集它时所处的条件中被使用。一个没有永久回退的运行时会在构造时被拒绝，而不是被容忍。

## 5. 公布的负载

只有当工作内容永不改变时，基准测试才能与自身相比较，所以每一份负载都是固定的、程序化的，且不含任何字体文件、图像文件或素材。字形掩码来自一个带种子的生成器，重采样源也是如此，而这个生成器是一个十七行的 `xorshift64*`，选择它恰恰是因为没有任何编译器升级能改变它所产生的输出。相隔半年的两次运行，一次在笔记本上，一次在手机上，绘制出完全相同的像素。

五者全都绘制进同一个参考目标，1080 乘 2340，一部竖屏、三倍密度的手机，因为目标正是一个后端必须分配、清空并交出的东西，而跨不同目标尺寸进行比较会把目标成本折算进比较之中。

| 负载 | 它的用途 |
|---|---|
| `glyphs.tiny` | 四个短掩码。GPU 输掉的情形：提交的开销比混合还大。 |
| `glyphs.paragraph` | 一屏文本。许多小掩码覆盖在一个大部分透明的平面上。 |
| `resample.card` | 一个 512 的估算被缩放进一张卡片。一次带硬边缘的流式读取，双线性和最近邻在此处可见地不一致。 |
| `blur.panel` | 在一块面板上进行的三趟 box blur。带暂存缓冲区的读-改-写。 |
| `mixed.screen` | 一个批次中的全部三个类别。调度器真正据以决策的粒度，也是切换成本被测量所依据的那份负载。 |

`glyphs.tiny` 的存在是为了成为一个 GPU 输掉的情形，而 `mixed.screen` 的存在是为了成为这样一个情形：对整个批次只作一个决策，要么对整批都是对的，要么就是明显错的。这些形状被选定是为了让套利变得可见，而不是为了看起来像一个真实的屏幕。

## 6. 运行它

```
cargo test --workspace
cargo build --workspace --release
cargo run --release --bin erl-raster-bench -- --help
```

bench 会链接这个平台构建所提供的任何流水线，并在两种状态下驱动公布的负载穿过它们全部。

```
usage: erl-raster-bench [--quick] [--thermal <state>] [--save <path>]

  --quick             run the short configuration: hot regime only, few iterations
  --thermal <state>   nominal, fair, serious, critical or unknown (default: unknown)
  --save <path>       write the device profile to a file when the run finishes

Only a run at nominal thermal pressure produces durations that may be compared with another run.
```

它什么都不决策。它打印它链接了哪些流水线、一张时长表，包含每份负载、每个状态和每条流水线的中位数、第九十五百分位、像素数量和移动字节数、一份无法被测量的东西的清单并附带原因、每份负载和每个状态下最快的流水线及其第二名与它的差距、来自单一类别负载的每个类别下最快的流水线，以及每个有序对被测量出的切换成本。使用 `--save` 时，它会写出调度器稍后将会读取的性能档案。

有三条规则被逐字遵守。时钟属于 harness，没有任何东西是手工计时的。测量只在标称热压下才是绝对的，这就是为什么热状态来自命令行而不是来自猜测，也是为什么当它不是标称时，报告会打印一条警告。一台机器上的首次运行没有基线，也绝不与某个已存储的性能档案进行比较。

一个格式错误的参数是一个错误，而不是一个被悄悄忽略的默认值，因为在一份没有人选择过的配置下产生的报告，是一份没有人能解读的报告。

## 7. 项目现状

已完成并验证：

- Rust 工作区，四个 crate，契约已稳定，`cargo test --workspace` 通过。
- 完整的 CPU 后端：标量参考实现，以及 AArch64 上的向量化合成行，两者产生相同的字节。
- 其他后端必须满足的、仅用整数的确定性参考实现。
- 公布的、无素材的负载集合。
- 带两种状态的对比 bench、交错的 harness、被丢弃的预热、被测量的切换成本，以及带版本号的设备性能档案。
- 第一个 GPU 桥，在 macOS 上通过 Metal。它在公布集合上复现标量参考实现，经测试验证。
- 自适应运行时：迟滞、每帧一次移动的预算、关键窗口、对未测量切换的拒绝、永不移除的回退，以及对性能档案的热检查。

尚未完成：

- Android 桥。它是同一道 `GpuSurfaceBridge` 接缝背后的第二个适配器，带它自己的平台门控。
- 应用集成：一个从同一组接口定义生成的 JSI 和 TurboModule 绑定，以及宿主视图，这样一个 React Native 组件就能把一个批次交给运行时。
- 零拷贝路径：iOS 上的 `IOSurface` 和 Android 上的 `AHardwareBuffer`，那道接缝早已为此成形。它是一条待测量流水线的一个变体，而不是被偷偷塞进基线的东西。
- 一个一致性测试运行器，它在整个公布集合上把每个后端与参考实现进行比较，把声明的容差当作数据而不是当作测试。
- 持续集成，为 `aarch64-apple-ios` 和 `aarch64-linux-android` 编译这个工作区。

## 8. 路线图

1. Android Vulkan 桥，位于现有的接缝之后。
2. 一致性运行器，以及当作数据的容差表。

## 9. 为什么这个文件里没有数字

因为在一台发热手机上的时长描述的就是一台发热手机。项目自己的规则是，在标称热压以上，没有任何测量是有效的，而一个被抄进 README 的数字会丢失让那个数字有意义的那一样东西：它被采集时所处的条件。数字属于 bench 打印出的报告，以及它保存的性能档案，紧挨着采集它们时所处的设备、平台和热状态。在你自己的硬件上运行它。
